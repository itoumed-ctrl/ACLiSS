# ACLiSS 構成・セキュリティ説明メモ（フェーズ5時点）

情報セキュリティ部門への説明資料のベースとして、フェーズが進むごとにこのファイルを更新していきます。

## ① システム構成図

**当面（私物スマホ運用・外部クラウド構成）**

```
[私物スマホ / iPad ブラウザ]
        │  HTTPS（インターネット経由）
        ▼
[Next.js フロントエンド（ホスティング先は今後選定）]
        │  HTTPS
        ▼
[Supabase（外部クラウド・無料枠）]
   ├─ データベース（容器マスタ・検査項目マスタ）
   └─ ストレージ（容器写真）
```

**将来（病院スマホ運用・院内イントラ構成／スコープ外・参考）**

```
[病院スマホ]
        │  院内ネットワーク内
        ▼
[院内イントラ内サーバー（DB + 画像）]
```

→ フロント側は `src/lib/config.ts` の環境変数（接続先URL）を差し替えるだけで
　将来この構成に移行できるようにしておく。

## ② 通信経路と保存データ一覧

- 通信は「私物スマホ ⇔ 外部サーバー（Supabase等）」の一方向のみ。
  電子カルテなど院内の他システムとは一切連携しない。
- 保存するデータは容器・検査項目のマスタ情報のみ（患者個人情報・要配慮個人情報は保持しない）。
- 通信はHTTPSで暗号化する（ホスティング先の標準対応を利用）。
- PWA化に伴い、Service Worker（`public/sw.js`）がマスタデータ・容器写真・画面を
  端末のブラウザキャッシュに保存する。保存先は端末内のみで、Supabase以外の
  外部サーバーには送信しない。保存内容はマスタ情報のみで、これも患者個人情報・
  要配慮個人情報を含まない。

## ③ 認証・アクセス制御の仕組み

- データベース（Supabase）は Row Level Security を有効化し、`containers` / `test_items`
  は「読み取り（select）のみ」を許可。書き込みはサーバー側の管理画面API（`service_role`キー、
  フェーズ2で実装）からのみ行える設計にしてある（`supabase/schema.sql`）。
- 容器写真はSupabaseストレージの公開バケット（`container-images`）に置く想定。個人情報を
  含まないため閲覧は公開でよいが、書き込み（アップロード）は管理画面経由に限定する。
- 管理画面（`/admin`）: 合言葉による簡易認証を実装済み。合言葉が一致しない場合、
  CSV取り込み・CSVダウンロード・容器/検査項目の個別追加編集削除・写真アップロード・
  パスワード変更のAPIは401エラーを返し実行できない。
- マスタCSVダウンロード（`/api/admin/export`）: 現在のマスタを、`/api/admin/import`が
  読み取る列名・順序と完全に一致する形式でCSV出力する。ダウンロードしたファイルを
  編集してそのまま取り込みフォームへ再アップロードできる（往復編集の運用を想定）。
  Excelで開いた際に文字化けしないようUTF-8のBOMを付与しているが、取り込み側の
  papaparseはBOMを自動的に読み飛ばすため再アップロード時に問題は起きない
  （往復させても1列目が壊れないことをテスト済み）。写真関連の列（`image_url`,
  `image_path_raw`）や`updated_at`はCSV一括更新の対象外のため出力しない。
- マスタの個別編集（`/api/admin/containers`, `/api/admin/test-items` とその`[code]`配下）:
  CSVでの一括更新とは別に、1件だけの追加・修正・削除を行える。upsertは渡した列だけを
  更新するため、容器写真（`image_url`/`image_path_raw`、写真アップロード機能専用）は
  このAPIでは一切変更しない。容器の削除は、その容器コードを参照する検査項目が残っている
  と外部キー制約でエラーになり、分かりやすいメッセージに変換して返す。
  ログイン画面自体も、入力した合言葉をサーバー側API（`/api/admin/verify-passcode`）で
  照合してから管理画面を表示する（以前は入力さえあれば中身が見えてしまう不具合が
  あったため修正済み）。
  合言葉はSupabase上の `admin_settings` テーブルにハッシュ値（SHA-256）のみ保存し、
  管理画面から自由に変更できる（Vercelの環境変数を触らずに即時反映される）。
  `anon`キーからはこのテーブルを一切読めない設計にしている。
- **メンテナンスモード（`admin_settings.maintenance_mode`）**: 管理画面から切り替えると、
  看護師が使う画面（トップ・スキャン・容器一覧・検査項目検索・最低採血量）へのアクセスを
  `/maintenance`（メンテナンス中の案内画面）へリダイレクトする。状態は `admin_settings`
  テーブルに保持し、リクエストごとに必ず実行される`src/proxy.ts`（ミドルウェア）で判定する。
  当初はレイアウト（共通の親コンポーネント）側で判定していたが、Next.jsのクライアント側
  ナビゲーションでは共通レイアウトが再利用され遷移先ごとに再評価されないことがあり、
  「メンテナンス画面のリンクは反応しているのに表示が切り替わらない」という不具合になった
  ため、リクエスト単位で確実に実行されるミドルウェアでのリダイレクト方式に修正済み。
  管理画面（`/admin`）自体は対象外とし、メンテナンス中でも解除操作ができる。
  切り替えAPI（`/api/admin/maintenance`）は合言葉必須。
- **Face ID / Touch IDでの解錠（任意設定、`src/lib/faceIdUnlock.ts`）**: 管理画面を
  スマホ・タブレットの生体認証で開けるようにする、端末内の利便性機能。PWAはネイティブ
  アプリと異なり、Face IDをサーバー側の認証として直接使うには本格的なWebAuthn/パスキー
  基盤が必要になるため、そこまでは実装していない。代わりに、利用者が明示的に「設定する」
  を押した場合のみ、合言葉をその端末のlocalStorageに保存し、次回以降はFace ID/Touch ID
  （WebAuthnのプラットフォーム認証器）で解錠してから自動入力する方式にしている。
  実際の認証（合言葉が正しいか）はこれまで通り`/api/admin/verify-passcode`で毎回
  サーバー側で行われる。**合言葉はその端末のブラウザに平文で保存される**ため、共用端末
  では設定しないよう画面上に注記している。合言葉を変更した場合、変更した端末では自動的に
  保存内容も更新されるが、他の端末で以前設定したFace ID解錠は次回失敗し、その時点で
  自動的に解除される（保存済みの古い合言葉で認証しようとして401になるため）。
- マスタ更新の操作ログ: CSV取り込みのたびに、いつ・誰が（任意入力）・何件更新したかを
  `import_logs` テーブルに記録する。
- 検索エンジンにインデックスされないよう `robots.txt` で全ページのクロールを禁止済み。
- **閲覧側（看護師利用画面）: 現在は認証なしで誰でもアクセス可能。**
  当初案ではBasic認証（合言葉）を実装していたが、依頼者の判断により
  「当面はパスワード不要のフリーアクセスでよい」という運用方針に変更した
  （フェーズ3〜4時点の実装は一時的にBasic認証ありだったが、フェーズ5でロールバック）。
  マスタに患者個人情報・要配慮個人情報を含まないことを前提とした判断だが、
  URLを知っていれば誰でも中身を閲覧できる状態である点は情報セキュリティ部門への
  説明時に明示する必要がある。将来的に閲覧制限を復活させる場合は、以前実装していた
  HTTP Basic認証の構成を再度組み込むことで対応できる。
- **アクセスログ（`src/proxy.ts`）**: 閲覧側の認証がない代わりの対策として、
  トップ・スキャン・容器一覧・容器詳細・検査項目検索・管理画面へのアクセスを
  日時・パス・IPアドレス・ブラウザ情報とともに `access_logs` テーブルにすべて記録する。
  以前はCookieで発行する匿名の端末識別ID（`acliss_device_id`）も併せて記録し、
  IPアドレスが変わっても同一端末からのアクセスかを判断できるようにしていたが、
  不要と判断し廃止した（Cookie発行・記録・管理画面での表示をすべて削除）。
  画面内のリンクはNext.jsが画面表示時に裏側で先読み（プリフェッチ）するため、
  実際に開いていないページまで記録されてしまう問題があった。プリフェッチ用の
  リクエストはヘッダーで見分けがつく想定だったが、実際には通常の画面遷移と
  区別できないリクエスト形になっていたため、ヘッダーでの判定だけでは防げなかった。
  最終的にログ対象のページへのリンク（トップ画面の各ボタン、容器一覧・検索結果の
  行、各画面の「ホーム」リンク）すべてに`prefetch={false}`を指定し、先読み自体を
  発生させない形で解決した。
  管理画面（`/admin`、合言葉必須）では、「管理画面の合言葉認証に成功した時」
  （`event: admin_login_success`、認証は`/api/admin/verify-passcode`成功時に記録。単にページを
  開いただけで認証が通っていない記録は除外）、「容器詳細を開いた時」（バーコード・容器一覧・
  検査項目検索のどこから開いた場合も対象）、「最低採血量計算ツールを開いた時」に絞って表示する
  （トップページ・容器一覧・検査項目検索の一覧表示自体は件数が多くなりすぎるため除外）。
  初期状態では折りたたみ表示にした上で直近200件のみ表示する（記録自体は絞り込まずすべて保持）。
  このテーブルもanonキーからは読めない。

## ④ なぜ当面は外部クラウドを使うのか

私物スマホからは院内イントラ内のサーバーへ直接アクセスできないため
（院内Wi-Fi接続時を除く）。マスタに要配慮個人情報を含めないことを前提に、
当面はSupabase（外部クラウドの無料枠）を利用し、将来病院スマホ運用へ移行する際に
院内イントラへ移設する。

## 現時点（フェーズ5）で担保されていること／いないこと

- ○ 担保: DBスキーマ・RLS設計（読み取り専用の公開、書き込みはサーバー側限定）
- ○ 担保: 患者個人情報・要配慮個人情報を含まない列構成（Excelマスタの列とそのまま対応）
- ○ 担保: 管理画面の合言葉認証（DB保存・管理画面から変更可能）、マスタ更新の操作ログ、
  robots.txtによる非公開設定
- ○ 担保: Supabaseの接続情報（URL・anon・service_role）をすべて設定済み
- ○ 担保: 看護師が使う画面（バーコードスキャン・容器一覧・検査項目検索・最低採血量計算）が動作する状態
- ○ 担保: 最低採血量計算ツールは項目データ・計算ルールをすべてアプリ内に持ち、Supabaseや
  外部サーバーとの通信なしに端末内だけで完結する（患者個人情報・要配慮個人情報は扱わない）
- ○ 担保: PWA化（ホーム画面追加・オフラインキャッシュ）。キャッシュ内容も
  マスタ情報のみで、保存先は端末内に限定
- ○ 担保: QRコード・院内掲示用ポスターの生成スクリプト
- △ 意図的な選択: 閲覧側の認証なし（依頼者判断による、フリーアクセス運用。
  代わりにIPアドレス付きのアクセスログを管理画面から確認できる）
- ○ 担保: ホーム画面追加時のアイコン・faviconに正式ロゴ画像（`assets/acliss-logo.png`）を反映
  （画面上部のヘッダーは引き続き仮デザインのまま）
